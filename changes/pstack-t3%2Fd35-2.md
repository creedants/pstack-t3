- kind feature
- `brigade.py set --notify '<command>'` records an opt-in outside ping in `restaurant.json`, and `set --notify ''` clears it. The command is split into words with no shell. A value that cannot be split is refused and nothing is written
- the command runs once, after the triggering command has finished and released the store lock, with one plain line as its last argument. It runs when `86 add` parks a new decision, and whenever `next --failure stuck` runs, which is how a wake reports a paused queue or a provider failure it cannot fix. It runs at no other time, and not when `86 add` returns a decision already open for the same dish
- the line names the restaurant and says a decision is waiting or work hit a failure it cannot fix. It never holds the question text, and its only variable part is the restaurant name, which a filter replaces with `brigade` when the name as typed, or its slug, looks like a thread id, path, email, token, or URL. The name is checked before it is slugged, so `alice@example.com`, `https://example.com`, `/srv/private-project`, and `www.example.com` all ping as `brigade`, and a name with an underscore does too
- a command that fails, cannot start, or runs past about 10 seconds prints one warning line, and on a timeout the command's whole process group is killed so a child it forked does not outlive the call. It never changes the exit status, the printed result, or the store write of the command that triggered it
- `status` ends with `outside ping: on` when a command is set, and `set` prints `on` in place of the command. A restaurant that never sets `--notify` sees no change in any output, and no schedule is created
- the `set` merge code moved to `commands/_setting_merges.py` with no behavior change, because `commands/setup.py` was near its size cap
