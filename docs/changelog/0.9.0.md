## 0.9.0 (2026-10-30)

### New

- `ticket sweep` prints the first 32 hex digits of a sha256 over the listed tickets as its digest
- `ticket sweep` refuses the list and the apply when rail.tsv holds a repeated ticket id, and it names the id and changes nothing
- `ticket sweep` refuses the list and the apply when a row of rail.tsv has a malformed or missing filed date, and it changes nothing
- `ticket sweep` digests each listed ticket's id, kind, goal, summary, and filed time, so a change to any of them makes the digest the owner approved stale and leaves the store unchanged
- `ticket sweep --older-than <n>` lists waiting tickets filed strictly more than `<n>` days ago that have no kind or no goal, with a count line and a digest of the listed tickets, and prints nothing to sweep when empty
- `ticket sweep --older-than <n> --drop --confirm <digest>` drops each listed ticket with a reason naming the sweep, and only when the digest still matches
- `ticket sweep --older-than <n> --goal G<n> --confirm <digest>` gives each listed ticket with no goal that goal, never overwrites a goal in goals.tsv, validates the goal before any write, and only when the digest still matches
- a sweep never touches an assigned, done, dropped, or moved ticket, a ticket with both kind and goal, or a waiting ticket that an item in flight names
- a rerun after an apply that leaves no further change prints nothing to sweep and exits 0 before the digest compare
- `brigade.py pass record --verdict send-back` refuses a call with no `--reason` before the store lock is taken. It exits 1 with one line naming `--reason` and its six values, and writes no row and no lock file. A panel member's send-back row needs a reason too, because every send-back row needs one
- `--reason` with any other verdict is still refused, and every other verdict still records with no `--reason`
- a `pass.tsv` row with an empty reason still loads and still counts as unrecorded in `pass stats`
- `brigade.py close` prints a `## Send-back reasons` section, with the reasons recorded in the window counted by reason. It counts non-member rows with the counting code `pass stats` uses, counts an empty or unknown reason as unrecorded, and prints `No send-backs` with the window's own wording when the window holds none. `close`, `close --dry-run`, and the file `close --to-file` writes carry the same section
- the `pass record` reference, the review reference, and the generated command page state the `--reason` rule for a send-back
- `brigade.py pass hits [--last DAYS]` prints a read-only table with one row per verifier seat recorded in `pass.tsv`: rounds reviewed, passes, pass-with-edits rounds, send-backs, upheld findings, overruled findings, and the upheld rate. The window is `--last` days back from now, default 7, and the command takes only the shared read lock `pass stats` takes and writes no file
- a send-back is upheld when the same dish's next recorded round is a pass at a different SHA, and overruled when the next recorded verdict is a pass at the same SHA or when the dish's round-budget decision was answered `known limits` or `drop` after it with no later non-member row of the dish at another SHA. A later round at another SHA that is not a pass upholds nothing. A send-back that neither rule settles counts in neither. A pass-with-edits round is upheld when `edits.tsv` recorded the edits from that round's SHA and that round's report, and counts in neither otherwise. A row counts for its own verifier seat, including a `--member` row and a `--late` row. The command help states every definition, and the generated command page carries the same text
- `brigade.py close` prints a `## Reviewer hit rate` section next to the send-back reasons section, with one counter line per verifier seat and the same counts, built from the same function. A week with no reviewed round prints `No reviewed rounds in the last 7 days.` `close`, `close --dry-run`, and the file `close --to-file` writes carry the same section
- rows recorded before this change load unchanged, and a `pass.tsv` row with an empty `sha` or `member` cell counts as it did before
- `$B dish D1 --usage-limit <provider/model> --role <role> --error <file>|- --catalog <file> --parent <provider/model> [--author ...] [--options <json>]` runs `roles.py backup` with the error text and records nothing when it answers `not-usage-limit`, records one cooldown row in `threads.tsv` for the failed seat and one `cooldown` event in `log.tsv`, and prints exactly one next step: `relaunch on <provider/model>`, `relaunch on <provider/model> options <json>`, `panel on <provider/model>, <provider/model>; rule <json>`, or `parked until <end>`
- the command lives on `$B dish` because `commands/__init__.py` is the only place a top-level subcommand is registered, `$B dish` owns the item, its attempt number, its state, and `threads.tsv`, and `--worker-ended` already sets the precedent of an exclusive dish flag family. `$B model` is restaurant-wide seat health with no dish and no attempt
- the printed target is the complete one `roles.py backup` resolved, so its `options` JSON follows the seat when the seat names options, and a panel prints each of its seats and then its `rule` JSON
- the cooldown event records that same complete replacement, or every panel seat, plus the panel rule, and a parked event records an empty replacement, no seats, and an empty rule
- the retry chain is the number of the dish's `log.tsv` rows of kind `dish` whose state ends an attempt, that is `sent-back`, `queued`, `passed`, `merged`, or `dropped`, so a send-back or a bounce starts the next attempt's chain and a replacement worker, a fresh verifier, and a park all keep the same one
- the cooldown event records its chain and whether that chain already spent its retry, so a second limit error in one attempt and role, including one on the seat the first error retried to, parks the dish and moves a dish in progress to `blocked` while a dish in review stays in review
- a park before any retry was sent records `spent` false, so a later report at the same chain asks `roles.py backup` again
- the cooldown ends at the reset time the error names, in an ISO date-time that names a zone, a clock time with `UTC`, `GMT`, or `Z` that is still ahead of now, or a relative span, and at now plus the new `cooldownMinutes` setting when it names none. `$B set --cooldown-minutes` sets that window, which defaults to 60 and refuses anything under 1
- an ISO stamp with no zone and a clock time that has passed are not read, and a relative span too large to represent is not read either, so the cooldown falls back to now plus `cooldownMinutes` when no shape is read, with no exception
- `$B watch` prints `cooling <provider/model> until <end> (<dish>)` for each live cooldown after the `skipped` lines, every live cooldown provider is passed to `roles.py backup` as `--out`, and a cooldown whose end has passed is not passed and prints nothing
- `$B close` prints a `## Seat cooldowns` section naming each cooldown's dish, seat, start, end, and the suggested replacement, and prints no section when the store records none
- `brigade.py brief` writes one brief file per attempt. The item's first launch writes `briefs/<dish>.md` and a later launch writes `briefs/<dish>-<k>.md`, where `k` is the attempt number the launch's worker row in `threads.tsv` gets, which is one more than the worker rows the item already holds when the brief is written. A brief a worker was launched with is never overwritten
- the brief prints the file's absolute path, then one launch sentence holding that path and the store root. The file holds the brief text alone, and the store root comes from the store's own path
- `$B launch` and `$B dish <id> --usage-limit` read the mode through `current_brief_mode` in `commands/tools.py`, whose file comes from `current_brief`, the newest attempt file at or below the next launch's number. After `dish --thread` records a launch, the probe lands on the file that launch read, so a hand-edited older file changes no seat
- `brief_seat_mode` is gone, so `commands/tools.py` holds the only reader and `brief_mode` names the file it refused
- `$B contract` is unchanged. The contract is a separate file, `briefs/<dish>.contract.md`, written on every brief
- a restaurant setting `prCredit` is a JSON boolean that "open --pr-credit on|off" records and "set --pr-credit on|off" changes, and any other value is refused with one line and changes nothing
- a missing `prCredit` reads as off, and a present value that is not a boolean is refused like every other malformed setting
- a new read-only command `$B credit D<n> --coordinator <provider/model>` prints one line naming the coordinator, the distinct authors, and the distinct verifiers of every pass.tsv row of the item, in first-recorded order, and leaves out every part that names no recorded value
- `credit` prints `credit: off for this restaurant; set --pr-credit on to turn it on` when `prCredit` is off or unrecorded, and exits 1 with the usual error for an unknown item
- `onboard` lists `pr_credit` as missing until it is recorded and names `open --pr-credit on or set --pr-credit on` as its fix
- review, script, store-config, and onboard docs name the new command and setting, and the review submit step puts the credit line last in the PR body
- edits verify runs the landing contract's setup command in its replay copy before the build and check commands

- brigade opening offers the contract setup command as a worktree-create script with `t3_project_update` after the user says yes, and never replaces or edits an existing script
- a store records a line every worker brief prints once under STANDING RULES with a `[standing rule]` tag in `house-rules.md`, after the built-in lines and never under STANDING ORDERS
- a recorded line the CONTEXT or VERIFY already states is not printed again, and neither is one an earlier printed line already states, and it prints as the store wrote it with no placeholder filled in
- the worker's houseRulesCap share counts every recorded line once as `- ` plus the line with no newline, whether or not a given brief drops it, while the reviewer and coordinator sizes do not count it

- A coordinator can opt in to GitHub issue webhooks. A signed webhook wakes it when an issue opens or reopens, and it files that issue as a ticket. - `land.py init` and `land.py status` print one warning on stderr when the contract's mode is `push` or `local` and the contract has no checks: nothing gates a landing, and `land.py init` again with `--check <command>` adds one. The warning is advice only. It changes no exit code, and `merge` and `human` mode print nothing new

### Fixed

- `pass record` skips a line of a report's `## Threads` section that starts, after any leading whitespace, with neither a list marker nor a `#`, and holds no backticked thread id, even when the line names a child role. A list marker is a hyphen, an asterisk, a plus, a bullet, or a number followed by a dot or a closing parenthesis. A backticked thread id is a backticked value holding a colon and holding no whitespace.
- `tests/brigade/reviews/test_threads_prose_roles.py` pins a prose line naming a child role under the list, a list row under that prose line, and a malformed list row under it
- `tests/runner_tests/support.py` takes a pidfd for each process it records, and `RunnerCase.end` signals that process only through the pidfd
- `tests/runner_tests/support.py` records a pid read from a mark only where the mark carries the start time `/proc` reports for that pid, so a stale mark naming a pid the kernel reused records nothing
- `tests/runner_tests/support.py` writes a mark only from the report it is given, and `mine`, `sleeper`, and `orphan` build that report from the pid and the start time the process it names reads for itself before it can exit, so `mark` reads no start time for a numeric pid it is given
