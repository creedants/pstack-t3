# Brigade

Read [the pstack-t3 runtime](../pstack-runtime/SKILL.md) before spawning workers, choosing models, scheduling, or isolating work. It maps those steps onto T3's orchestrator tools.

Brigade copies the setup Lauren Tan runs with Cursor Projects. The user is the executive chef. Each restaurant is one project, or one focus area inside a project. Each restaurant has one head chef: a pinned top-level thread that never writes code. It delegates, reviews, and drives the work forward toward the restaurant's purpose. The user moves between restaurants and reviews what landed.

Every mechanism here comes from pstack. Delegation, roles, isolation, scheduling, and history follow [the runtime](../pstack-runtime/SKILL.md). Workers run poteto-mode playbooks.

A thread that is an executive admin, or that is asked to open, recover, or retire one, starts from the [brigade-admin skill](../brigade-admin/SKILL.md).

## Terms

| Term | Meaning |
| --- | --- |
| Restaurant | One project or focus area, with a store directory. A project may hold several. |
| Head chef | The restaurant's coordinator thread. |
| Menu | `menu.md`: purpose, what good looks like, what is off the menu, budget. |
| House rules | `house-rules.md`: the standing orders a worker brief pastes. |
| Ticket | One incoming request on the rail (`rail.tsv`). |
| Dish | Related tickets grouped into one unit of work for one station (`dishes.tsv`). |
| Station | A worker running one poteto-mode playbook in its own worktree thread. |
| Pass | The review of a dish against its tickets and the menu (`pass.tsv`). |
| 86 | A decision only the user can make (`86.tsv`). |

These words name files, commands, and steps. They never appear in speech. Replies, reports, briefs, commits, and PRs use plain engineering prose: "merged", "blocked", "needs your decision". Never "plated", "86'd", "heard", or "chef".

## Operating stance

- Run to the next real blocker. "Should I continue" is never a question. Reply as Run a service step 9 says for this restaurant's reporting level.
- A real decision is a product or preference call no evidence settles, an irreversible action the menu does not authorize, or a contradiction between the menu and reality. Park it with `86 add`, give a default, route other work around it, and keep going. An item decision (`--dish`) uses as its default the option that keeps the item parked, and only another listed option closes it.
- Raise a decision once, in the reply where you park it. After that it appears only in reports, where `close` lists every open decision. Never repeat it as "still open" in other replies.
- Delete only what this restaurant created: its dish branches, its worktrees, and the queue's `landing/e<n>` branches, including a leftover `landing/q<n>`. Ask before deleting any other branch, even one fully merged.
- Never write code yourself. Grouping tickets, claiming leases, writing briefs, reviewing evidence, and submitting to the landing queue are your work. Code changes and conflict fixes are dishes.
- Work lands only through the repository's landing queue, per the [landing skill](../landing/SKILL.md). Several restaurants can share one repository. The queue and its leases keep them off each other.
- `handoff.md` is `<restaurant dir>/handoff.md`. Rewrite handoff.md at a quiet point before compaction. After any compaction, read handoff.md, house-rules.md, and the memory index before acting.

## The script

`<skills>/brigade/scripts/brigade.py`, where `<skills>` is the directory holding this skill. Every command but `open` and `walk` takes `--at <restaurant dir>` or `BRIGADE_DIR`. It prints one line or a short block, in plain prose.

```bash
B="python3 <skills>/brigade/scripts/brigade.py --at <restaurant dir> --owner <thread>@<generation>"   # the token from status
$B next [--failure fixable|stuck] [--unsent <kind>] [report-back <dish> | review <dish> --verdict pass|send-back|blocked|pass-with-edits | checks <dish> --result pass|fail | merge <dish> | liveness | intake | morning | evening | user [--question] | admin <request>]   # steps this wake owes and reply
$B status                                    # thread <id> or thread not recorded, the counts, reports to <thread> when set, and owner <thread>@<generation> when a generation is recorded
$B set --thread <id> [--replace] --schedule <name>=<id>
$B set --reporting every-turn|milestones|digest
$B set --liveness-ms <N>                     # the interval a new liveness schedule uses, a whole number of at least 60000; "" removes it
$B set --schedule <name>=                    # drops that name from restaurant.json
$B set --intake github,<feed>                # the intake sources this restaurant owns
$B set --workers <n>                         # dishes in progress or in review at once
$B set --autofire off|urgent|normal|low      # the lowest ticket priority startable lists as startable
$B set --reports-to <thread>                 # the executive admin this restaurant reports through
$B set --mode light|full                     # this restaurant's mode from the next brief
$B set --build-command "<command>" --check-command "<command>"   # the two commands edits verify runs
$B set --cap KIND=N[,KIND=N]                 # the cap on items of that kind holding a worker slot
$B set --review KIND=full|light[,KIND=MODE]   # the default mode for a new item of that kind
$B ticket add --summary "<request>" --kind feature|fix|polish|upkeep|study [--goal G<n>] --source user|github|<feed> [--ref <ref>] [--request A<n>] [--again] [--priority urgent|normal|low] [--paths src/a,src/b] [--decision]   # prints T<n>. --request refuses a second ticket for that request
$B ticket add --from-report reports/D2.md [--dry-run]   # one waiting ticket per follow-up in that report. It prints a `not filed` line for prose it does not take as a follow-up, and a `skipped` line for follow-up text already on the rail
$B ticket list [--state waiting|assigned|moved|done|dropped]
$B ticket set T3 [--state dropped] [--priority urgent|normal|low] [--paths src/a,src/b] [--decision | --no-decision]   # at least one flag
$B ticket set T3 --kind fix [--goal G1 | --no-goal]   # changes a waiting ticket
$B ticket move T3 --to <sibling>             # hands a waiting ticket to a sibling. Prints the thread to tell
$B ticket take                               # files every ticket a sibling handed to this restaurant
$B ticket paths [--dry-run]                  # on each waiting ticket that records no paths, records the tracked paths its summary quotes in backticks
$B startable                                 # the workers line, then a count line and each waiting ticket in start order with why it can or cannot start now, or no waiting tickets. It starts nothing
$B inbox take                                # ticket take, then prints each request from the executive admin as A<n>: <line>
$B inbox done A<n>                           # records the request as acted on and deletes its file
$B goal add --name "<name>" --purpose "<why>" --done "<test>" [--share <n>]   # prints G<n>
$B goal set G1 --state open|paused|done|dropped [--evidence "<one line>"]   # a move to done or dropped needs --evidence
$B goal set G<n> --state paused   # no ticket of that goal starts, not even as a ride-along
$B goal set G<n> --share N   # a ceiling of N worker slots holding that goal's items
$B goal list [--all]   # each open or paused goal, and each done or dropped goal that still has a waiting ticket, an item in flight, or a ticket riding along, with its state, name, counts, purpose, and done test, then the counts of unassigned work
$B fire --tickets T1,T3 --station bug-fix --summary "<outcome>" --paths src/a,src/b [--timebox 60] [--mode full --reason "<one line>"] [--kind <kind>] [--ride-along T3] [--doc-item]   # claims the lease, prints D<n>
$B brief D2 --fields <path>                 # JSON file, or --fields - for stdin. Writes briefs/D2.md
$B brief D2 --goal '...' --acceptance '...' [--acceptance ...] --contract '...' --verify '...' --base main [--context ...]   # same brief. Single-quote every field
$B contract D2                               # prints the contract the last brief of D2 stored
$B watch                                     # a line for every open dish; renews each live lease. A dish that owes its round decision gets <n> send-backs, decision pending. It prints one trunk line while it sees a red or unseen remote mode trunk. It stays silent with no contract or in local mode.
$B hang D1 --provider <provider> --minutes <n> [--attempt <n>]   # one open run after report-back, once per attempt
$B model skip <provider/model> --cause rate-limit|failed   # records that seat as skipped
$B model clear <provider/model>   # records a passing smoke test on that seat and clears its skip
$B thread <dish> --role "panel member" --thread <id> --seat <provider/model>   # records one thread an item used, for a role no other command writes
$B dish D2 --state dropped [--stopped <run id>|idle]   # releases the dish's lease and returns its tickets to waiting
$B dish D2 --state in-progress|in-review|queued|merged [--thread <id>] [--task <id>] [--pr <url>] [--sha <head>] [--timebox <m>] [--reported] [--lease <id>] [--paths <paths>] [--branch <name>]   # --thread writes the open worker row of threads.tsv for the current attempt
$B dish D2 --mode full --reason "<one line>"   # records the item's move to full once
$B dish D1 --worker-ended "<reason>"   # records that this attempt's worker ended or failed and wrote no report
$B pass record D2 --sha <head> --verdict pass|send-back|blocked|pass-with-edits [--reason <reason>] --author <provider/model> --verifier <provider/model> [--pr <url>] [--note "..."] [--same-family] [--report <file>] [--edits <file>] [--reviewer-thread <id>] [--member | --late]   # --reviewer-thread writes the reviewer row of threads.tsv for this attempt. Once the dish owes its round decision, each send-back it counts ends its line with <n> send-backs, decision pending
$B pass check D2 --sha <head> [--json]       # exits 1 unless that SHA passed. --json prints verdict, author, verifier, note, and crossFamily
$B pass stats [--last N]   # first-pass rate overall and per author model over the last N items; default 20
$B edits verify D2 --from <reviewed sha> --to <head>   # exits 1 when a compared path differs or the build or check command fails
$B 86 add --question "..." --options "a, b" --default "a" [--dish D2]   # prints Q<n>
$B 86 add --dish D2 --round-budget           # the decision D2 owes at three send-backs. prints Q<n>
$B 86 answer Q1 --answer "..." ; $B 86 list
$B close [--dry-run | --to-file]             # report of what changed since the last one. --to-file prints only the written file's path
python3 <skills>/brigade/scripts/brigade.py walk [--repo <project root>]
python3 <skills>/brigade/scripts/brigade.py affected --paths <file> [--paths <file>...] | --diff <base>   # verify paragraph for those paths; reads the store's restaurant.json for the affectedTests layout and prints the store's check command when no layout is set
L="python3 <skills>/landing/scripts/land.py --repo <project root>"   # leases and the landing queue
```

Read [script.md](script.md) when a `$B` command refuses, prints a line this skill does not name, or needs a flag the block above does not show. `$B <command> --help` prints every flag.

Run affected to print the verify paragraph for a path change. It scans the tree and names the modules or the full suite. Use the picked modules for worker verification. Leave the full suite to CI and the merge queue unless affected reports an unmapped path.

`affected` reads the layout from the store's `restaurant.json`, which may hold one optional `affectedTests` object. Its seven keys are `always`, the required dotted module every modules result includes; `workflowModule`, an optional dotted module a `.github/workflows/` path maps to; `entryPoints`, the required list of repository paths that the helper modules load or run; `helpers`, an optional list of repository paths; `suite`, the optional whole-suite command; `python`, the optional absolute path of the second interpreter; and importRoots, the optional list of repo paths tried as prefixes for absolute imports in candidate order after the loader directory and the root with every match kept; relative imports never search them, and an absent importRoots means the directories of entryPoints and helpers. Without the key the picker is off, and a brief with an empty `--verify` runs the store's `checkCommand` instead, or says no verify command is set. This template preserves this repository's picker paragraph after replacing `<path to a Python 3.10 interpreter>` with the existing interpreter path:

```json
"affectedTests": {
  "always": "tests.test_pstack_t3",
  "workflowModule": "tests.test_run_tests",
  "entryPoints": ["t3/added/brigade/scripts/brigade.py", "t3/added/landing/scripts/land.py"],
  "helpers": ["tests/brigade/support.py", "tests/landing/support.py"],
  "suite": "python3 scripts/run_tests.py -j 8",
  "python": "<path to a Python 3.10 interpreter>",
  "importRoots": ["scripts", "t3/scripts"]
}
```

The second interpreter is an absolute path whose file name is `python<major>` or `python<major>.<minor>`, and the paragraph names it by that version. A layout that sets `python` also needs a `suite` that starts with `python3`, because that interpreter replaces the leading `python3`. A store whose `checkCommand` is `none` records no check command.

`fire` reads the store's shared-document catalog and timebox from `restaurant.json`. `sharedDocs` is an optional list of `{"path": <repository path>, "kind": "file"|"skill"}`, and it defaults to an empty list. A `file` entry names one document, and a `file` entry whose path ends with `/` names a directory prefix, so files under it are documents. A `skill` entry names a directory, with or without its trailing slash, and its `SKILL.md` files are documents. `docTimebox` is an optional count of minutes, and it defaults to 90. `fire` refuses a lease holding a shared document when `--timebox` is over `docTimebox` or `--tickets` names more than one ticket, unless `--doc-item`. Without `sharedDocs`, `fire` refuses nothing for shared documents, and a successful `fire --doc-item` records the shared-document note `doc-item`. A present value that does not parse is refused, with nothing written and no lease claimed. This template reproduces this repository's catalog and threshold:

```json
{
  "sharedDocs": [
    {"path": "README.md", "kind": "file"},
    {"path": "docs/guide.md", "kind": "file"},
    {"path": "t3/runtime.md", "kind": "file"},
    {"path": "t3/setup.md", "kind": "file"},
    {"path": "t3/added/", "kind": "skill"},
    {"path": "t3/overrides/", "kind": "skill"},
    {"path": "skills/", "kind": "skill"}
  ],
  "docTimebox": 90
}
```

`fire` reads the store's change-note directory from `restaurant.json`. `changeNoteDir` is an optional repository-relative directory path, and it defaults to unset. Set it with `brigade.py set --change-note-dir <dir>` and clear it with an empty value. When it is set, `fire` leases `<dir>/<branch>.md` for the branch that attempt will use, with `%` written as `%25` and `/` written as `%2F`. When it is unset, `fire` leases no fragment. A present value that does not parse is refused when `fire` leases paths, with nothing written and no lease claimed. `fire` with no paths leases nothing and reads nothing. This template records this repository's directory:

```json
{
  "changeNoteDir": "changes"
}
```

Pass brief fields as a JSON file with `--fields <path>`, or from stdin with `--fields -`. Put every flag value in single quotes so the shell does not expand it. Before you write brief fields, read [Brief fields](script.md#brief-fields).

Each intake source has one owner. `set --intake`, and `open --intake` when it creates a restaurant, refuse a source a sibling already lists, with `brigade: <sibling> already owns intake from <source>; move tickets to it instead`. On an existing one it changes nothing. `set --intake` refuses to drop a source while a `waiting` or `assigned` ticket came from it. `ticket add --ref` refuses a ref that is already live here or in a sibling, with `brigade: <ref> is already T1 (waiting); nothing added`. The ref stays unchanged through every `ticket move` and `ticket take`. Before you file or update a ticket, change intake, or fix a malformed table line, read [Intake and refs](script.md#intake-and-refs).

The cap counts dishes in progress or in review. `fire` refuses before it claims a lease when the count is already there. A refused `fire` leaves the tickets waiting and logs why. When the cap is full, `dish --state in-progress` or `in-review` refuses when that dish is not already one of those states. Moving between those states, or replacing the worker, does not. `dish --lease` and `dish --paths` record a lease claimed again, and refuse a merged or dropped dish. When `fire` cannot release a lease it claimed and then could not keep, it warns with the lease id and the landing queue's diagnostic. `open` warns when `workers` is at or above the repository cap and a sibling exists. `watch` prints `waiting on L<n> (<holder>)`, `waiting for room in the repository (<n> of <n> changes in flight)`, `waiting for a worker (<running> of <cap> running)`, or `unblocked` with a shell-quoted `fire` command. Run that command as printed. Before you run `open --workers` or `fire` or change a dish's lease, paths, or branch, read [Worker cap](script.md#worker-cap). When `watch` or `ticket list` prints a worker, lease, or repository block, or `walk` prints a blocked count, read that section before acting on the block.

Every ticket has a priority. `urgent` is work that is broken, unsafe, or blocking, such as data loss, a broken install, a red trunk, a privacy or security hole, or an upstream sync. `normal` is wrong or missing behavior, a false statement in docs people follow, or a feature the user asked for. `low` is polish, a refactor, or an optional pointer. Set it at triage with `ticket add --priority`. Change it with `ticket set T<n> --priority` when the user says so or the facts change.

`status` prints `owner <thread>@<generation>`. Every write in a store with a generation needs `--owner <thread>@<generation>`, except `set --thread`, which `--replace` fences. The check runs under the store lock, and the lock is held through the write. A token that does not match exits 1 with `brigade: owner <token> is stale; this store is owned by <thread>@<generation>` and changes nothing. `set --thread --replace` first raises the landing floor for `<restaurant>/` with `land.py owner`, so `land.py` also refuses the replaced thread's `--owner <restaurant>/@<old generation>`. Before you run `set --thread`, read [Owner](script.md#owner).

On a dish that holds a lease and records a worker thread, `dish --state dropped` refuses without `--stopped`, with `brigade: D3 holds L4 and its worker may still be running; wait for its run with t3_thread_wait, then pass --stopped <run id>`. The lease stays active, so no sibling claims its paths early. Before you run `dish --state dropped`, read [Dropping a dish](script.md#dropping-a-dish).

`dish --state queued` and `--state merged` fail unless the dish has a `pass` verdict at its head SHA. `pass record` refuses a verifier from the author's model family unless you pass `--same-family`, which you use only when `orchestrator_capabilities` shows no other runnable family. `--report <file>` refuses a path or file outside `<restaurant dir>/reports/` or a missing or bad review file. The round budget stops another fix round. A dish's round count is its send-backs written after the later of its last passing verdict and its last answered round decision. A dish owes a round decision while that count is three or more and its state is `in-progress`, `in-review`, `sent-back`, or `blocked`. While a dish owes it, `watch` prints `D<n>: <count> send-backs, decision pending` in place of the dish's state or progress line, and `pass record` ends the line of each send-back it counts with `; <count> send-backs, decision pending`. `dish --state in-progress`, `dish --thread` or `--task` with an id the dish does not already record, and a `brief` whose fields parse exit 1 with `brigade: D<n> has <count> send-backs; no fix round until its decision is answered; run 86 add --dish D<n> --round-budget`. `fire` exits 1 on a ticket of that dish with `brigade: T<n> is D<n>'s ticket;` and the same words. The budget refuses nothing else. `$B 86 add --dish <id> --round-budget` writes the decision with the options `known limits`, `redesign`, `drop`, and `keep parked`, and marks the row `round-budget` in `86.tsv`. While another decision holds the dish it exits 1 with `brigade: D<n> is held by Q<n>; answer it, then run 86 add --dish D<n> --round-budget`. Only `known limits`, `redesign`, or `drop` closes it. No other decision's answer restarts the count. `ROUND_BUDGET` in `brigade.py` sets the number. Before you write report instructions for a worker or verifier, run `pass record` or `dish --reported`, or act on a review-report warning from `close`, read [Pass and round budget](script.md#pass-and-round-budget).

Each item runs in full or light mode per [the runtime's Modes section](../pstack-runtime/SKILL.md#modes). When the store changes meanwhile, `brief` resolves again, and after three changes it exits 1 with `brigade: D<n> changed while resolving its mode; run brief again`. `dish --mode full` refuses a queued, merged, or dropped dish. `--mode light` on an item exits 1. Before you run `brief` or pass `--mode` to `open`, `set`, `fire`, or `dish`, read [Mode](script.md#mode).

## House rules

`house-rules.md` holds the rules a worker brief pastes. `open` writes the file once, from a template, and never rewrites it. The template holds two project rules, the worker size limit, and the test standard. A store may edit or delete the last two.

A store created before the template held them gains them only when the user pastes them into its `house-rules.md`. Paste this text at the end of the file:

- You may write the change yourself when it changes one file outside tests, the added and removed lines outside tests are about 40 or fewer across the whole item, and the contract does not call its guarantee safety, privacy, or integrity. Count those lines from `git diff --numstat` against the item's base commit, quote that output in the report, and treat every round and commit as one diff. Past that size, or more than one file outside tests, the code delegate writes the change. The claims check and the gate review are never skipped.

1. A test earns its place when it fails for a defect that no other check reports; name that defect in the test name.
2. A test that pins a reviewed defect stays; remove it only with a mutation that shows another check fails for the same change.
3. Use a rule in the project's static check, when it has one, when the property is visible in the text or the tree without running the code, with one passing and one failing fixture test.
4. Use a test when the property is behavior: exit codes, written files, ordering, refusals.
5. Call the command in the test process through the project's in-process test helper, when it has one; start a process only for a race, a signal, exit status, the environment, or help output, and say which.
6. Never assert a library's own wording.
7. Add a case to an existing table when the setup is the same.
8. A test that sleeps to order two processes names the review finding it pins.
9. Do not add a test for what the project's build already refuses.
10. The reviewer asks of each new test: which change to the code makes this fail and nothing else fail?

## First service

A head chef's first wake runs [First service](opening.md#first-service) in opening.md, then Run a service.

   - While this restaurant has dishes queued, keep a landing drain schedule per the [landing skill](../landing/SKILL.md#keep-the-queue-moving), and delete it when none are. Name the reporting level in that prompt, and say to follow Run a service step 9. After the queue opens a PR, that section has this thread call `watch_pull_request` and run `land` on each wake. Other restaurants' drains on the same repository are harmless. The queue lock runs one at a time. When you delete that schedule, run `$B set --schedule drain=`.
   - While `$B watch` prints anything other than "no work in progress", and on the first refused `fire`, keep a liveness schedule. `watch` renews every live lease, so this schedule is what keeps a lease from expiring. Take `everyMs` from the `liveness:` line of `$B status` every time you create or recreate the schedule, so the new schedule uses the store's stored interval, or the reporting level's default when none is stored: `{"type": "interval", "everyMs": <that number>}`. The prompt is "Use the brigade skill. You are the head chef for the restaurant at `<restaurant dir>`. Reporting level: `<level>`. Follow Run a service step 9. Run the liveness check." Delete it when `$B watch` prints "no work in progress". When you delete that schedule, run `$B set --schedule liveness=`. After `$B set --reporting` moves the level to or from `digest`, read `$B status` again and, when the number on its `liveness:` line changed, delete the running liveness schedule, create it again at that number, and record the new id with `$B set --schedule liveness=<id>`.
   - Record each ID with `$B set --schedule <name>=<id>`. When the landing drain schedule is recreated, record the new id with `$B set --schedule drain=<id>`. Report schedules only in a reply Run a service step 9 already allows. At `digest`, creating, recreating, or deleting a schedule is not a reply occasion. The IDs stay in `restaurant.json`, and `list_scheduled_tasks` shows each cadence and `nextRunAt`. A first service started by opening the restaurant, and a reply to a user's level change, may name the schedules within Digest messages. This overrides the runtime's "Report the returned cadence and `nextRunAt`" for a head chef at `digest`.

## Filing tracker work

Coordinators and the executive admin follow this section before each `ticket add` for a user request or a supplier finding. The tracker is the one AGENTS.md names. Read its open items with the commands AGENTS.md names. Run `gh issue list` only when AGENTS.md names no other tracker. The rail records the work a restaurant runs. It is not the project's tracker.

1. **Match.** A ref the request names is its ref. Otherwise read the open items and find the one item that is the same work as the request, by its summary. Pass that item's ref as `--ref` and create nothing. When more than one item could be the same work, create nothing and add the ticket with no `--ref`. A scope that forbids tracker writes still passes an existing item's ref.
2. **File.** When no item matches, follow AGENTS.md's filing rules. Create an item only when those rules call for one and the user or the house rules allow that write. Pass the ref the tracker prints for it. When the rules or the permission do not allow the write, create nothing and add the ticket with no `--ref`.
3. **Unavailable.** When the tracker cannot be read, report it and fetch nothing in its place. A user request is still filed. Pass the ref it names as `--ref`, and omit `--ref` only when it names none. A supplier finding with no ref adds no ticket.
4. **Refusals.** A refused `ticket add` is not an error to work around. Four of its refusals are about the request. A live ticket here or in a sibling has the ref. A ticket of this restaurant already carries the `--request` id. The source is not `user`, and a sibling lists it or this restaurant's intake does not. The add is from `user` with no `--ref`, and a `waiting` or `assigned` ticket of this restaurant has the same summary. Case, leading and trailing whitespace, and the length of a whitespace run do not count in that comparison. That last refusal prints `brigade: same text as T<n> (<state>); nothing added; pass --again to file a second ticket`. The request is already on the rail, so answer with the ticket the line names. Pass `--again` only when the request is separate work in the same words. `--again` lifts no other refusal. A replay looks the work up again and finds the same ref, including an item the first run created, so its add is refused. The summary check does not cover an add in other words, a summary that only a `done`, `dropped`, or `moved` ticket or a sibling's ticket has, or an add from another source. So read `$B ticket list` before you file a no-ref request again.

## Run a service

Every wake runs this: a user message, a worker's report-back, a verifier's completion, a schedule, or a `watch_pull_request` wake.

0. **Next.** Run `$B next` first. Pass `user` for a user message. Pass `report-back <dish>` for a worker report. Pass `review <dish> --verdict <verdict>` for a verifier completion. ### Digest messages

## Git and PR housekeeping

The head chef owns every git and PR chore its work creates. In `merge` and `push` mode the user has no step. In `human` mode the user merges each PR. In `local` mode the user merges `refs/landing/<trunk>` into a branch.

- Write each PR's title and body through `submit`, and link every PR with `link_pull_request`.
- Keep the landing drain schedule while anything is queued or awaiting merge, per the [landing skill](../landing/SKILL.md#keep-the-queue-moving). After the queue opens a PR, also watch it as that section says. Keep that watch across reports while the entry is queued or awaiting merge. When you delete the schedule, run `$B set --schedule drain=`. Call `unwatch_pull_request` only when this thread stops driving that PR.
- Finish with the old worker when a dish merges, is dropped, is sent back, bounces, or is replaced after a contested report. The old worker is the thread the dish row names before any `$B dish <id> --thread` records a replacement. Name that thread id in every call below, so the replacement's open run is never touched. Read it with `t3_thread_read`. If its run is still open after the report-back, run step 1 of the three drop steps in [Run a service](#run-a-service) step 7, call `$B hang <id> --provider <provider> --minutes <n>` with the provider and the minutes that read showed, then run step 2 and read the worker's activity again. Archive with `t3_thread_organize`, `action: "archive"`, and that `threadId` only after the worker's run is terminal and its child work is no longer pending. When the wait times out or child work remains, keep the thread and finish cleanup on a later service. A worker that an earlier attempt launched counts too. Check each attempt's thread, and for a run a replaced attempt left open, add `--attempt <n>`, counting attempts from 1 in launch order. If the run has already closed, archive it only when its child work is no longer pending. When that child work remains, keep the thread and finish cleanup on a later service. On a send-back or a bounce, finish before `$B dish <id> --state in-progress`. Entering in progress starts a new attempt, and `hang` then refuses with `brigade: no report-back on this attempt`. At `digest` reading, interrupting, logging a hang, and archiving send no reply of their own. A merge that drains the batch still sends the drain summary.
- After a dish merges, is dropped, is sent back, or is replaced after a contested report, remove the old worker's worktree, delete its branch locally and on the remote, and delete the queue's `landing/e<n>` branch, including a leftover `landing/q<n>`, once its PR merged or closed. After a send-back or a contested replacement, delete the old branch only once the fresh worker is launched, because its branch starts from the old head.
- After a landing, when the user's checkout at the project root is clean and on trunk, fast-forward it with `git merge --ff-only`. Otherwise leave it alone.
- A bounce or a conflict is a dish for a fresh worker, never a manual rebase.
- Never force-push trunk, rewrite published history, change branch protection, or delete a branch this restaurant did not create.

## Liveness check

Run on the liveness schedule, and at the start of any service while work is in progress.

1. `$B watch`. It prints one line per dish in progress, one line for each other dish not `merged` or `dropped`, one line per ticket moved to a sibling that has not filed it yet, and `handed to you: <n>; run ticket take` while siblings' handoffs wait in this restaurant's inbox. On `handed to you`, run `$B ticket take`. On `not delivered`, run the `ticket move` command the line prints, then message the sibling per Run a service step 2. `waiting for ticket take` needs nothing until the sibling's next service. For a waiting ticket whose latest log row is `blocked`, it prints `waiting for a worker (<running> of <cap> running)`, `waiting on L<n> (<holder>)`, or `waiting for room in the repository (<n> of <n> changes in flight)`, the first that holds now. An `unblocked` line names a shell-quoted `fire` command. Run it as printed. That is the `fire` in steps 3 and 4 of Run a service for those tickets. When `$B status` prints `reports to <thread>` and a ticket's first `blocked` row in `log.tsv` is more than an hour old, read [Liveness](admin-reporting.md#liveness) before you send the `blocked` line.
   `watch` renews the lease of every dish in progress, in review, passed, sent back, or parked, and prints nothing for a live one. It updates `lastActivityAt` after a pass that renewed every live lease, so `walk` marks a restaurant whose leases stopped renewing. A submitted lease is the queue's. Act on these lines.
   - `D3: lease L4 expired; stop its worker, then run lease renew L4`. Run steps 1 and 2 of the three drop steps in step 7 without step 3 and wait for a terminal state before any renew. Follow [Lease lines](recovery.md#lease-lines).
   - `D3: lease L4 was released; claim again before submitting`. Claim the paths and record the lease before any submit. Follow [Lease lines](recovery.md#lease-lines).
   - `D3: could not renew L4: <error>`. Fix the landing store cause. Follow [Lease lines](recovery.md#lease-lines).
   - `D2: in review`, `D3: passed, not submitted`, `D4: parked`, and `D5: sent back` keep the liveness schedule alive. Act on them per Run a service steps 6 and 7.
   - `D1: 3 send-backs, decision pending`. Launch no fix worker. Follow the decision-pending bullet in Run a service step 7.
   - `D1: open decision Q1: <question>; launch no worker or verifier until 86 answer Q1`. Launch nothing and spawn nothing. Read no worker thread and send it no nudge. Skip Liveness steps 2 to 5 for that item. Act on a lease line printed under it. After `$B 86 answer` prints `Q<n> answered`, the ordinary line returns.
   - `D1: in progress with no worker thread; launch a fresh worker`. Launch a fresh worker per steps 4.3 and 4.4. Never call `t3_thread_send` on an earlier attempt's thread.
   - `D1: worker ended with no report; the recorded reason is <text>`. Never call `t3_thread_send` on the dead thread. Run the four steps the line prints, in order. Follow [Worker ended](recovery.md#worker-ended).
   - `skipped <provider/model> (<cause>); run model clear <provider/model> after a smoke test passes`. Launch no worker, verifier, or code delegate on that seat while the line prints. Follow [Skipped seat](recovery.md#skipped-seat).
   - For a passed or queued dish, `watch` reads `land.py status --holder <restaurant>/<dish> --sha <dish sha>` and takes the highest entry at exactly the dish's SHA. `D1: landed as E1 (<commit>); mark it merged`: run `$B dish D1 --state merged`. `D2: E3 awaiting merge <pr url>; watch that PR`: call `watch_pull_request` on that PR, because this thread owns it even when a sibling's `land` opened it. `D4: E4 bounced: <reason>`: follow the bounce step in Run a service step 7. `D5: E6 already submitted; mark it queued`: run `$B dish D5 --state queued`. That recovers a crash between `submit` and `dish --state queued`. `D6: E7 queued` needs nothing until the queue moves.
    - `trunk CI failing since <since>: <workflow> <url>`. `<since>` is the oldest consecutive failure in the last 100 runs. The lookup reaches the newest completed run and the oldest failure within the last 100 runs. Read the failing jobs. File or fire an urgent fix. Tell the owner. See the `next liveness` bullet below.
    - `cannot see trunk CI: <reason>`. The trunk state is unseen. No fix is owed.
    - `next liveness` and `next merge` owe the red trunk See cues while the stored trunk stays red. A store that does not report to an executive admin replies yes at every-turn, milestones, and digest. No cue when the stored trunk is green or unseen or unknown.
   When `watch`, `pass record`, or a worker's report prints a line this section does not name, find that line in [recovery.md](recovery.md) and follow its step.
2. "report written, no report-back" is a defect. Read the worker thread and find why the message never arrived. Follow [Report written, no report-back](recovery.md#report-written-no-report-back).
3. A "report written" line that does not say "no report-back", and a line `D<n>: reported Nm ago, not in review; read the thread (thread <id>)`, mean the worker reported back and its review has not started. Read the worker thread with `t3_thread_read`. If its run is still open, call `t3_thread_interrupt`, then `$B hang <id> --provider <provider> --minutes <n>` with the provider and the minutes that read showed. Then review per Run a service step 6. At `digest` this is a routine wake with no reply.
4. "over its timebox": `t3_thread_read` the thread with `view: "activity"` and `afterPosition`. When it made progress in the last 10 minutes, raise the timebox once with `$B dish <id> --timebox <m>`. Otherwise run steps 1 and 2 of the three drop steps in step 7 without step 3, then launch a fresh worker per steps 4.3 and 4.4 with a smaller scope, or park the dish with `86 add` when only the user can unblock it. Step 4.4 records that thread, and recording it starts the attempt while the dish stays in progress. The previous report and report-back mark belong to the worker you replaced. `$B watch` compares the report file to this new start.
5. `D<n>: running Nm of Tm (thread <id>)`: `t3_thread_read` the worker thread. When `activeRunId` is null and the latest run in `recentRuns` completed more than 10 minutes ago, the worker is idle with its timebox still open and no report for the current attempt. The `running` line already means that, even when an earlier attempt's report file remains, because `watch` compares the report to this attempt's start. `brigade.py` reads only the store, the clock, and the landing queue, so this check needs the thread read. Send the worker one nudge with `t3_thread_send`, mode `"auto"`, `clientRequestId` `nudge-<dish>-<that run id>`, and the line `Your thread has been idle since <completedAt> with no report. Check each open child with task_status, handle a stalled one per the runtime's Delegation step 5, then finish the brief.` A worker idle again after that nudge goes to step 4 as if over its timebox. Otherwise the line means nothing new. Reply per Run a service step 9. When `$B status` prints `reports to <thread>`, follow [Liveness](admin-reporting.md#liveness) and end the turn with no assistant text. Otherwise, at `milestones` this is a routine wake, so end with no reply, or with a single line when the host requires text. At `digest`, end the turn with no reply text at all. At `every-turn`, send a short reply. A dish in `in-review` or `passed` is not this line.
6. When `$B watch` prints "no work in progress", delete the liveness schedule with `delete_scheduled_task`, then run `$B set --schedule liveness=`. Delete it only on that line. A blocked ticket is not that line, so the schedule stays while one is waiting. Do not treat that line as a drained batch. A batch has drained when step 9 says it has. The drain summary is sent on the wake that first finds the batch drained. A review still pending means the batch has not drained. Do not send the drain summary while a review is pending. Reply per step 9.
