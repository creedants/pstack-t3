## Open a restaurant

Run from any thread.

1. Name the target project and focus. List projects with `t3_project_list`. A restaurant lives in exactly one T3 project, because a head chef can only read and steer threads in its own project.
2. Draft the menu from evidence: the repo's README and AGENTS.md, open work in the tracker AGENTS.md names, read with the commands it names, and recent threads via the **recall** skill. Use `gh issue list` only when AGENTS.md names no other tracker. When the named tracker cannot be read, say so in the draft. Never read GitHub Issues in its place. Ask the user only for what the evidence cannot settle, normally the purpose itself. Use the **grilling** skill when the purpose is vague.
3. Ask the user four things with the host's question tool, unless they already said each one. Ask all four in one call.
   - Who lands work. This decides whether the user stays a gate on PRs and git. Offer:
     - `merge` (recommended for a repository with a remote): every change still gets a PR as its record, and the queue merges it once the checks pass. The user reviews what landed afterward and does no PR or git work.
     - `human`: every change gets a PR, and the user merges it.
     - `push`: no PRs. The queue pushes trunk after the checks pass.
     - `local`: nothing leaves the machine. Changes land on a lane ref the user merges.
     Say that `merge` and `push` put reviewed changes on trunk with no human gate. When the repository already has a landing contract (`$L status`), its mode applies to every restaurant on that repository. Say so before changing it, and name the siblings `walk --repo <root>` lists.
   - How often the coordinator replies. Recommend `milestones`. Offer `every-turn`, `milestones`, and `digest`. What each level sends is [Run a service](SKILL.md#run-a-service) step 9.
   - Which mode, per [the runtime's Modes section](../pstack-runtime/SKILL.md#modes). Offer `light` (recommended) and `full`. Light keeps tests, the build, and a review by another model family, or a same-family read when only the author's family has a runnable seat, and cuts the panels around them. When the user has no preference, record nothing, and the project and user roles files decide.
   - Whether pull requests credit the models that did the work. Offer `on` and `off`. Record the choice with `open --pr-credit on|off` in step 4.
4. Run `python3 <skills>/brigade/scripts/brigade.py open --project-root <root> --name "<restaurant>" --reporting <level> [--workers <n>] [--mode light|full] [--pr-credit on|off]`. It prints `opened <dir>` or `exists <dir>`, then one block per sibling coordinator on the same project root. Each block names that coordinator, its store directory, its thread, its purpose, and what it does not take. Fill `menu.md`. Keep this purpose clear of every sibling `open` printed. Under `## Off the menu`, list each sibling's purpose as that sibling's work. Append house rules. The list is forbidden paths, the verification bar, intake sources, `--workers`, and the repository's hot shared files, and where their changes go instead. Run `$B set --intake <sources>` with each intake source the house rules name, except a source a sibling's `restaurant.json` already lists. That sibling owns it and moves you the tickets that are yours. Name the repository's own hot shared files from evidence and record them with `$B set --shared-docs`. A README and the main guide are common examples, not a fixed list. A change adds its change-note bullets as a file under the store's `changeNoteDir` directory when the store sets one, and does not edit a hot shared file for them. A store with no `changeNoteDir` records no fragment. Set it with `brigade.py set --change-note-dir <dir>`. It edits a hot shared file only when its ticket is about it, or when it removes or renames something the file names. Otherwise the worker lists that doc edit under follow-ups in its report. `fire` refuses requested `--paths` covering a shared document from the store's `sharedDocs` catalog when `--timebox` is over the store's `docTimebox`, default 90, or `--tickets` names more than one ticket, unless `--doc-item`. The default level is `milestones` when `--reporting` is omitted. Opening an existing restaurant does not change its level. Change it later with `$B set --reporting <level>`. `open` records the mode only when it creates the restaurant. Change it later with `$B set --mode`. At creation, `--pr-credit on` records `prCredit` as `true`, and `--pr-credit off` records `false`. Omitting the flag leaves the key unset, which reads as off. An existing restaurant keeps its saved setting. Change it later with `$B set --pr-credit on|off`. The context cap open and set write is [Context cap](#context-cap).
5. Set the repository's landing contract to the choice. When `$L status` shows no contract, run `$L init --mode <choice>` per the [landing skill](../landing/SKILL.md#set-up-a-repository-once), with the repository's own test and type-check commands as checks. When it shows another mode, run `$L mode <choice>`. It names the holders of unreleased leases. Then tell each sibling the new mode with `t3_thread_send`, to the threads `walk --repo <root>` prints. The landing contract is the only record of the mode. House rules do not restate it. When a house rule already states the mode, report the duplicate, say that the landing contract wins, and leave the rule in place unless the user says to remove it.
6. Offer the repository setup command as a worktree-create action. Read it with `python3 <skills>/brigade/scripts/brigade_lib/brief_setup.py --project-root <root>`. That command prints the setup command and nothing else, and it prints nothing when the contract records none. Read the project with `t3_project_read`. When it printed a command and no existing project script has `runOnWorktreeCreate` true, show the command and ask with the host's question tool whether to save it as a worktree-create script. This writes the user's T3 project settings, so it asks first. On yes, call `t3_project_update` with the existing script list plus one new script holding that command, `runOnWorktreeCreate: true`, and the other fields the tool requires. `t3_project_update` replaces the whole script list, so send the existing list with the new script appended and keep every existing script unchanged. On no, on an empty print, when such a script already exists, or when either project tool is absent, record nothing and continue. Never replace or edit an existing script. An older T3 Code build may lack the script field, and the setup bullet in every worker brief covers it by telling the worker to run that command before its first build or test.
7. Launch the head chef only when `open` printed `opened`. That word goes to the one caller that created the directory. When `open` printed `exists`, do not launch. When the output includes `thread <id> already recorded`, that thread is the coordinator. An `exists` coordinator with no recorded thread is the user's call. Two threads never write one store. `$B set --thread` refuses to replace a recorded thread unless you pass `--replace`. When `open` printed `opened`, launch with `t3_thread_launch`: `projectId` of the target, `workspaceStrategy: {"type": "root"}`, title `Head chef: <restaurant>`, and a `message` that says "Use the brigade skill. You are the head chef for the restaurant at `<restaurant dir>`. Run your first service." Record the returned `threadId` with `$B set --thread <id>`.
8. Tell the user where the thread is and which landing mode the repository uses. If it is in another project, you cannot read or message it after launch. That is expected.

Opening a restaurant is the user's request for top-level threads: the head chef, and one worktree thread per worker.

## Onboard

Onboard detects what the repository and the store already configure. Run this section in place of Open a restaurant step 3. For a first opening, complete Open a restaurant step 4 once during step 3 below, keep its opened or exists result for step 7, and continue at step 5 afterward. A settings check uses the existing store and launches no coordinator.

1. Use the name from the request or current store. Otherwise use the project directory name as a candidate for round one. Run `python3 <skills>/brigade/scripts/brigade.py onboard --project-root <root> --name "<restaurant>" --detect`. It prints facts and missing as JSON and writes no brigade files. Each store setting names its state and its fix. Every other row carries a fix, and only repository cap, trunk, remote, required checks, PR ability, and contract checks carry None. Missing lists the settings to ask about plus restaurant when no restaurant file exists, in table order.
2. Build one HTML page with a flow chart of intake, tickets, fire, worker, review, landing queue, merge, and report. Pin each missing setting to its step and include the question details below. Check it with html_preview, then publish it with html_render before asking. If either tool is unavailable, print the same flow and question details as plain text.
3. Use answers already in the request. Ask only the remaining missing settings and confirm the detected repository facts with the host question tool in at most two rounds. When the tool is unavailable, print the questions as a plain text list and read the answers as a reply. Include setup-pstack model choices in these rounds. For a first opening, run Open a restaurant step 4 once with the answers, then apply remaining answers with set, land.py, or setup-pstack. For an existing store, use set for changed store settings. Record confirmed detected build and check commands as contract checks with `land.py init --check` when detection did not list them as missing. `set --build-command` and `set --check-command` still write the store.
4. Run the same command with `--summary` in place of `--detect`. It writes `onboarding.txt` in the restaurant directory, one `name: value` line per fact. A rerun prints only the change lines, as `name: old -> new`, plus `added` and `removed` lines. Identical bytes print `no change to onboarding.txt` and leave the file untouched. Before `open` it prints the lines it would write, then `not saved`, and writes nothing.

### The flow in words

Intake collects requests from the sources the restaurant owns. The intake question decides which sources this restaurant reads. Tickets wait on the rail. Per [Run a service](SKILL.md#run-a-service) step 3, the coordinator groups waiting tickets before firing. Fire records the ticket ids the caller passes. Fire checks the worker cap before the lease claim for its paths and again after it. The brief command writes a brief. The workers question caps parallel dishes. The mode question picks the playbook depth for the brief. Per [Run a service](SKILL.md#run-a-service) step 4, the worker runs one playbook in its own worktree thread. Review records a verdict from another model family, or the same family with --same-family, after [Run a service](SKILL.md#run-a-service) step 6 reads the report and diff. The landing queue records the lease id, runs the contract setup and checks, and merges, polls, or pushes the change, or records a lane ref. The landing question picks the queue mode. The queue reads the generated path list, the rebuild command, and the contract setup and checks. It never reads the map. The map guides brigade claims and affected paths. Only the recorded build and check commands guide edits verify and affected reports. Detected values guide nothing until set records them. The change note directory names a queue path through its fragment. The generated map adds its expansions to the lease. Merge and push modes put the reviewed change on trunk. Human mode leaves the PR for the user to merge. Local mode records a lane ref. The required checks reading lists the detected trunk's required names. A protection read that GitHub answers with HTTP 404 gives none, the unprotected state. A non GitHub remote gives unknown. The PR ability reading gives unknown for a non GitHub remote. The contract checks reading lists the recorded contract checks. Per [Run a service](SKILL.md#run-a-service) step 9, report tells the user what landed. The reporting question picks how often.

### The questions

Read [Onboard questions](reference/onboard.md) when Onboard asks a question or reports a value as missing.

### The two rounds

Round one asks only unanswered choices for missing restaurant, landing mode, models, and mode settings. Confirm a candidate restaurant name here. If the name changes, rerun --detect for that name before writing. Round two asks any remaining missing settings and confirms detected repository facts. Two rounds are the maximum. Never re-ask a configured setting. When the host question tool is unavailable, print both rounds as one plain text list.

### The summary file

`onboarding.txt` holds one `name: value` line per fact, in table order. Rerun `--summary` after any `open`, `set`, `land.py init`, `land.py mode`, or `roles.py write` change. The rerun prints `added`, `removed`, and `old -> new` lines for changes to the parsed summary values. Treat that output as the checklist for the reply. When the rerun prints `no change to onboarding.txt` the bytes matched and the file stays untouched. When it prints `normalized onboarding.txt with no fact changes` the parsed facts matched despite different bytes and the rerun rewrote the file. Say so and move on.

## First service

1. `t3_thread_organize` with `action: "pin"` and no `threadId`, acting on the caller on purpose.
2. Call `orchestrator_capabilities` and resolve roles per [the runtime's Roles section](../pstack-runtime/SKILL.md#roles). The roles files hold the budget. Seats are resolved per item in Run a service steps 4 and 6.
3. Create three schedules with `schedule_task`, bound to this thread, each with a self-contained prompt: "Use the brigade skill. You are the head chef for the restaurant at `<restaurant dir>`. Reporting level: `<level>`. Follow Run a service step 9. Run a service." Read `<level>` from `restaurant.json` (`every-turn`, `milestones`, or `digest`). A missing `reporting` field is `milestones`. Add the purpose of the run to each. A later `$B set --reporting` changes the level, and the next service reads `restaurant.json` rather than the level copied into an older prompt.
   - Morning service: `{"type": "fixed_time", "timeOfDay": "09:00"}`. The prompt carries the reporting level.
   - Intake: an interval matched to the sources in the house rules, at least `3600000`. Skip it when the menu names no source. A restaurant whose `restaurant.json` has `reportsTo` keeps this schedule even with no source, at `3600000`, because each service starts with `inbox take`. The prompt carries the reporting level.
   - Evening report: `{"type": "fixed_time", "timeOfDay": "18:00"}`, prompt adds "Write the report." The prompt carries the reporting level.

The landing drain schedule, the liveness schedule, and recording each schedule id are in [First service](SKILL.md#first-service).

4. Rerun `python3 <skills>/brigade/scripts/brigade.py open` with the same project root, name, and reporting level. Two coordinators opened at the same moment both see template purposes, so this step runs once those menus can be filled. Compare each sibling purpose it prints with this coordinator's `menu.md`. Keep this purpose clear of those siblings. Add any missing sibling purpose under `## Off the menu` as that sibling's work. A sibling that prints `purpose: not written yet` has not filled its menu. Leave that sibling out of this menu until a later `open` prints a purpose.
5. Run a service.

## Rename a restaurant

Run `$B open --project-root <root> --name <old> --rename <new> --owner <thread>@<generation>`. It rewrites the stored name and the `# Menu:` and `# House rules:` first lines stating the old name, then moves the directory last. A failed write restores the prior bytes, and a rerun moves a store that records the new name. It refuses dishes other than merged or dropped, a different project root, an existing target other than its own recorded empty reservation, and admin, handoff, or held landing references outside the store. Delete each schedule naming the old path, recreate it against the new directory, and record its id with `set --schedule`. Send each thread naming the old path the new directory with `t3_thread_send`, or relaunch it with a prompt naming the new one.

## Close a restaurant

First, for every dish that still holds an active lease, run the three drop steps in Run a service step 7: `t3_thread_interrupt`, then `t3_thread_wait`, then `$B dish <id> --state dropped --stopped <run id>` only after a terminal state. `$B close` writes reports and releases nothing. When any wait returns `timedOut: true`, stop here. Keep every schedule, so `watch` keeps that lease renewing, and continue closing on a later service once every wait has reported a terminal state. Then call `unwatch_pull_request` on each PR this thread is still watching. Delete its schedules with `delete_scheduled_task`, then clear each recorded name with `$B set --schedule <name>=`. Run `$B close` one last time, or `$B close --to-file` at `digest`. That close is the closing reply step 9 names. Unpin the thread with `t3_thread_organize`. Leave the store. It is the record.

## Context cap

The context cap is stored in `restaurant.json`, and reads as 300000 when no `contextCap` key is stored there. When `coordinatorProvider` reads as `claude`, the cap is written to the project's `.claude/settings.local.json` as `autoCompactWindow` only in the cases the paragraphs below name.

Creating a store writes that file only when the caller passes `--context-cap` or `--coordinator-provider`, and the effective provider reads as `claude`. A creation with neither flag records no cap and writes nothing under the project root, and an integer `autoCompactWindow` the file already holds stays as it is. Creation with `--context-cap N` writes `N`. Creation with `--coordinator-provider claude` and no `--context-cap` writes the 300000 default.

Opening an existing store never writes the settings file. When the store records a `contextCap` and that file does not hold it, `open` prints one drift line. The line names the integer the file holds and the effective cap, or says the file holds no integer cap, and names the command that writes the cap. No line prints when the file already holds the cap, when the store records no cap, and when the provider is not `claude`.

On a `claude` store, `set --context-cap N` writes the settings file, and `set --context-cap ""` writes the 300000 default into it. A successful write replaces an untracked settings file symbolic link with a regular file and leaves the link's target unchanged. A refused write exits 1 and leaves the settings file as it was. On a host that is not Claude, the context cap is not enforced and no settings file is written.
