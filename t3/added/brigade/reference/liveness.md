# Liveness

Read this on the liveness schedule. The core keeps step 1 short form, step 5 nudge, the held item, and the pending decision. This file holds watch lines and steps 2 to 6.


1. `$B watch`. It prints one line per dish in progress, one line for each other dish not `merged` or `dropped`, one line per ticket moved to a sibling that has not filed it yet, and `handed to you: <n>; run ticket take` while siblings' handoffs wait in this restaurant's inbox. On `handed to you`, run `$B ticket take`. On `not delivered`, run the `ticket move` command the line prints, then message the sibling per Run a service step 2. `waiting for ticket take` needs nothing until the sibling's next service. For a waiting ticket whose latest log row is `blocked`, it prints `waiting for a worker (<running> of <cap> running)`, `waiting on L<n> (<holder>)`, or `waiting for room in the repository (<n> of <n> changes in flight)`, the first that holds now. An `unblocked` line names a shell-quoted `fire` command. Run it as printed. That is the `fire` in steps 3 and 4 of Run a service for those tickets. When `$B status` prints `reports to <thread>` and a ticket's first `blocked` row in `log.tsv` is more than an hour old, read [Liveness](../admin-reporting.md#liveness) before you send the `blocked` line.
   `watch` renews the lease of every dish in progress, in review, passed, sent back, or parked, and prints nothing for a live one. It updates `lastActivityAt` after a pass that renewed every live lease, so `walk` marks a restaurant whose leases stopped renewing. A submitted lease is the queue's. Act on these lines.
   - `D3: lease L4 expired; stop its worker, then run lease renew L4`. Run steps 1 and 2 of the three drop steps in step 7 without step 3 and wait for a terminal state before any renew. Follow [Lease lines](../recovery.md#lease-lines).
   - `D3: lease L4 was released; claim again before submitting`. Claim the paths and record the lease before any submit. Follow [Lease lines](../recovery.md#lease-lines).
   - `D3: could not renew L4: <error>`. Fix the landing store cause. Follow [Lease lines](../recovery.md#lease-lines).
   - `D2: in review`, `D3: passed, not submitted`, `D4: parked`, and `D5: sent back` keep the liveness schedule alive. Act on them per Run a service steps 6 and 7.
   - `D1: 3 send-backs, decision pending`. Launch no fix worker. Follow the decision-pending bullet in Run a service step 7.
   - `D1: open decision Q1: <question>; launch no worker or verifier until 86 answer Q1`. Launch nothing and spawn nothing. Read no worker thread and send it no nudge. Skip Liveness steps 2 to 5 for that item. Act on a lease line printed under it. After `$B 86 answer` prints `Q<n> answered`, the ordinary line returns.
   - `D1: in progress with no worker thread; launch a fresh worker`. Launch a fresh worker per steps 4.3 and 4.4. Never call `t3_thread_send` on an earlier attempt's thread.
   - `D1: worker ended with no report; the recorded reason is <text>`. Never call `t3_thread_send` on the dead thread. Run the four steps the line prints, in order. Follow [Worker ended](../recovery.md#worker-ended).
   - `D1: idle since <time> with no report (thread <id>)`. The dish is in progress with a worker thread and has no report for the current attempt. It prints at once when the latest T3 run ended. It prints for an open run only when its thread updated_at is at least 10 minutes old. Read the thread with `t3_thread_read` before acting.
   - `skipped <provider/model> (<cause>); run model clear <provider/model> after a smoke test passes`. Launch no worker, verifier, or code delegate on that seat while the line prints. Follow [Skipped seat](../recovery.md#skipped-seat).
   - For a passed or queued dish, `watch` reads `land.py status --holder <restaurant>/<dish> --sha <dish sha>` and takes the highest entry at exactly the dish's SHA. `D1: landed as E1 (<commit>); mark it merged`: run `$B dish D1 --state merged`. `D2: E3 awaiting merge <pr url>; watch that PR`: call `watch_pull_request` on that PR, because this thread owns it even when a sibling's `land` opened it. `D4: E4 bounced: <reason>`: follow the bounce step in Run a service step 7. `D5: E6 already submitted; mark it queued`: run `$B dish D5 --state queued`. That recovers a crash between `submit` and `dish --state queued`. `D6: E7 queued` needs nothing until the queue moves.
    - `trunk CI failing since <since>: <workflow> <url>`. When the failure streak ends inside the last 100 runs, `<since>` is the oldest consecutive completed failure. When the window holds 100 runs and every fetched completed run from the newest completed run to the end of the window failed, `<since>` is `before <createdAt of the oldest fetched run>` and the start is unknown. It stores red so the cues still fire. Read the failing jobs. File or fire an urgent fix. Tell the owner. See the `next liveness` bullet below.
    - `cannot see trunk CI: <reason>`. The trunk state is unseen. No fix is owed. When the window holds no completed run, the reason is `no completed run in the last 100 runs`.
    - `next liveness` and `next merge` owe the red trunk See cues while the stored trunk stays red. A store that does not report to an executive admin replies yes at every-turn, milestones, and digest. No cue when the stored trunk is green or unseen or unknown.
   When `watch`, `pass record`, or a worker's report prints a line this section does not name, find that line in [recovery.md](../recovery.md) and follow its step.


2. "report written, no report-back" is a defect. Read the worker thread and find why the message never arrived. Follow [Report written, no report-back](../recovery.md#report-written-no-report-back).


3. A "report written" line that does not say "no report-back", and a line `D<n>: reported Nm ago, not in review; read the thread (thread <id>)`, mean the worker reported back and its review has not started. Read the worker thread with `t3_thread_read`. If its run is still open, call `t3_thread_interrupt`, then `$B hang <id> --provider <provider> --minutes <n>` with the provider and the minutes that read showed. Then review per Run a service step 6. At `digest` this is a routine wake with no reply.


4. "over its timebox": `t3_thread_read` the thread with `view: "activity"` and `afterPosition`. When it made progress in the last 10 minutes, raise the timebox once with `$B dish <id> --timebox <m>`. Otherwise run steps 1 and 2 of the three drop steps in step 7 without step 3, then launch a fresh worker per steps 4.3 and 4.4 with a smaller scope, or park the dish with `86 add` when only the user can unblock it. Step 4.4 records that thread, and recording it starts the attempt while the dish stays in progress. The previous report and report-back mark belong to the worker you replaced. `$B watch` compares the report file to this new start.


5. `D<n>: running Nm of Tm (thread <id>)`: `t3_thread_read` the worker thread. When `activeRunId` is null and the latest run in `recentRuns` completed more than 10 minutes ago, the worker is idle with its timebox still open and no report for the current attempt. The `running` line already means that, even when an earlier attempt's report file remains, because `watch` compares the report to this attempt's start. `brigade.py` reads only the store, the clock, and the landing queue, so this check needs the thread read. Send the worker one nudge with `t3_thread_send`, mode `"auto"`, `clientRequestId` `nudge-<dish>-<that run id>`, and the line `Your thread has been idle since <completedAt> with no report. Check each open child with task_status, handle a stalled one per the runtime's Delegation step 5, then finish the brief.` A worker idle again after that nudge goes to step 4 as if over its timebox. Otherwise the line means nothing new. Reply per Run a service step 9. When `$B status` prints `reports to <thread>`, follow [Liveness](../admin-reporting.md#liveness) and end the turn with no assistant text. Otherwise, at `milestones` this is a routine wake, so end with no reply, or with a single line when the host requires text. At `digest`, end the turn with no reply text at all. At `every-turn`, send a short reply. A dish in `in-review` or `passed` is not this line.


6. When `$B watch` prints "no work in progress", delete the liveness schedule with `delete_scheduled_task`, then run `$B set --schedule liveness=`. Delete it only on that line. A blocked ticket is not that line, so the schedule stays while one is waiting. Do not treat that line as a drained batch. A batch has drained when step 9 says it has. The drain summary is sent on the wake that first finds the batch drained. A review still pending means the batch has not drained. Do not send the drain summary while a review is pending. Reply per step 9.
