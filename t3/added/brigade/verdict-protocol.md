# Verdict protocol for gate reviews

Read-only review. Change no tracked file in the repository. Run no git commit, push, or GitHub write. Work in a detached temporary worktree or scratch copy of the reviewed SHA when you need to run or edit anything, and remove it afterwards. Your only lasting write is the review report.

Scratch copies. Never change the repository's git configuration, in any checkout or worktree: no `git config`, no `core.worktree`, no `--work-tree` against the shared git directory, no `git init` inside it. To get a scratch copy of a commit, use `git archive <sha> | tar -x -C <tmp dir>` (no git metadata), or `git worktree add --detach <tmp dir> <sha>` followed by `git worktree remove --force <tmp dir>` when you finish. Before you write the report, run `git -C <the reviewed worktree> status --short` and it must run without error.

What counts as a blocker. Judge only what this diff adds or changes; a flaw in a line the diff did not touch is a note. A statement in skill text, docs, help text, a printed message, a docstring, a comment, or a test name that is false or broader than the code. A behavior that breaks the brief's acceptance or the repository's rules in AGENTS.md. A change-note bullet only when it states something false; a true bullet that omits a condition is a note. Style preferences are notes.

Concurrent changes. A failure that needs another program to change the filesystem or a database between two adjacent system calls of the tool is a note, not a blocker, unless this diff makes the tool's outcome in that case worse than it was at the base, or the brief names that case as in scope. Say which of those applies when you raise one.

Worth a round. A blocker costs a fix round and a second review, so it must be worth one. For each blocker, name who is harmed, misled, or exposed in normal use under the brief's trust model, and how. A true finding that needs an input or a state the trust model makes very unlikely, and whose effect is small, is a note. Put it under the non-blocking notes with one line saying why it is not worth a round and a one-sentence ticket the coordinator can file. Two exceptions. A breach of a property the brief's guarantee calls safety, privacy, or integrity stays a blocker however rare; add the line `Rare:` with your reason when you judge it so, and the coordinator may rule it an accepted limit. A blocker the reviewer does not mark `Rare:` is not one the coordinator may accept as limit. A statement that is false stays a blocker, because the fix is an edit and costs no round.

Find every blocker in this one pass. Read every statement the diff adds or changes, not a sample. A later round checks only the fix and the points that failed, so anything missed now lands.

The first line of the report is exactly one of these.

- `Verdict: pass`. No blocker.
- `Verdict: pass with edits`. Every blocker is wording (skill text, docs, help text or a printed message that no test asserts, a docstring, a comment, a test name, or the change note) or a small code fix. A small code fix changes at most 20 lines in total across all edits, including any test lines, and you ran the listed checks green in your scratch copy with it applied. A blocker that breaches a safety, privacy, or integrity guarantee the brief names is never a small code fix; write `Verdict: fail` for it. `edits verify` applies that cap to the applied change and refuses the head while the count is over it. It counts, for each file the edits change, every line that file adds and deletes from the reviewed commit, so a replaced line counts two and a last empty line counts one. It skips a path that ends in `.md`, and a `.py` path whose code lines are the same once its comments, its docstrings, blank lines, and trailing whitespace are removed, so comments and docstrings alone are wording. It counts a printed message or a test line in a `.py` file, because that changes the code lines, and it counts a `.py` file that either side cannot parse. For each one give an edit under a `## Edits` heading in exactly this shape, so a script can read it: a `### Edit <n>` heading, a line ``File: `<path>`, line <n>.``, a line `Old text:` followed by a fenced block, and a line `New text:` followed by a fenced block. The tool parses this section. Put the `File:` line first, then `Old text:` and its fenced block, then `New text:` and its fenced block. Write `Old text:` and `New text:` alone on their lines. Close each fence with a line of only backticks. A path is relative to the repository. An edit cannot create a file, so a blocker that needs a new file is a `fail`. Start each of those lines and each fence at the first column. Put an empty line above each `File:`, `Old text:`, and `New text:` line unless the line above it is the edit's heading, the closing line of a fence, or another of those three lines. Put nothing but empty lines between `Old text:` or `New text:` and its fenced block. Write the path in single backticks with no space after the opening backtick. A note inside an edit needs an empty line between it and the `File:`, `Old text:`, or `New text:` line below it. Do not put a fence inside a fenced block. The old text must occur exactly once in the file. Apply all your edits in your scratch copy, regenerate with the project's build command when a source of generated files changed, and confirm there that each new sentence and the sentences next to it are true against the code, and that the listed checks pass. Say so under `## Edits verified`. Give edits for source files only, never for a file the build generates.
- `Verdict: fail`. At least one blocker needs a change to behavior, to a test body, or to a string a test asserts. List every blocker with file and line, a reproduction you ran, and the smallest fix. Wording blockers in a failed review still come with their exact old and new text. When the whole fix for a blocker is a printed message plus the test lines that assert it, or a test name, still write `Verdict: fail`, give every edit including the test edits under `## Edits` in the shape above, apply them in your scratch copy, and say under `## Edits verified` that the checks pass there; such a report can land on your text with no second review.

After the verdict line: blockers, then edits when there are any, then non-blocking notes, then the commands you ran with their results.

Scratch space. When the review brief names a parent directory, make every scratch directory and archive copy with `mktemp -d -p <that parent>`. Never create them directly under `/tmp`, which is memory-backed and small on many systems. When the brief names no parent, say so in the report and do not use a memory-backed temporary directory. Delete your scratch directory when you finish. Do not set TMPDIR. A file name you report carries no home directory, user name, host name, or thread id of the machine that ran the review.

## Rounds after the first

Round one is unchanged. It reads the whole change against its base.

In round two and later, review `git diff <previous reviewed SHA>...<head>` and check each blocker the previous round named. The brief names that SHA and gives you the previous round's review file.

A new blocker must be in that fix diff or caused by it. Give a concrete reproduction you ran against the reviewed head.

Worth a round tests a finding this diff adds or changes. A defect that was present at the previous reviewed head and that the fix neither touches nor makes worse is outside this diff. It is a non-blocking note with one ticket line the coordinator can file, never a blocker.
