### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

[The runtime's Modes section](../../pstack-runtime/SKILL.md#modes) sets the mode lines of every brief this playbook writes and how its spawns run in light mode.

Spawn workers through `delegate_task` with `mode: "async"` and a target resolved from its role, per [the runtime's Delegation section](../../pstack-runtime/SKILL.md#delegation). Link each PR with `link_pull_request` and watch it with `watch_pull_request` per [Pull request watching](../../pstack-runtime/SKILL.md#pull-request-watching), with a `schedule_task` heartbeat fallback. Call `unwatch_pull_request` when the run finishes. Call no scripts except `roles.py` for roles and briefs and `land.py slot --` for local command capacity. Run no polling loops, and never relay messages or status between agents.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. An owner that outlives one turn is a top-level thread from `t3_thread_launch` with a worktree `workspaceStrategy`, per [the runtime's Top-level threads section](../../pstack-runtime/SKILL.md#top-level-threads).
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers cannot see their siblings. Run each worker as a `delegate_task` child with `mode: "async"`, isolated in its own worktree when it writes, per [the runtime's Isolation section](../../pstack-runtime/SKILL.md#isolation). Verify UI and CLI work through the control skill or T3 preview tools, per [the runtime's Verification surfaces](../../pstack-runtime/SKILL.md#verification-surfaces). Resolve each seat from its role per [the runtime's Roles section](../../pstack-runtime/SKILL.md#roles) and follow the Subagents section.
- **Sub-coordinator.** Only when one area has many parallel workers. A sub-coordinator is a `delegate_task` child that itself calls `delegate_task`. It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Reuse a worker only when the next step strictly needs its retained state,** such as its checkout, uncommitted changes, or a running process. Send that follow-up through `t3_thread_send` per [Fresh children by default](../../pstack-runtime/SKILL.md#fresh-children-by-default). Otherwise spawn a fresh child with consolidated scope. Never send to check on one, because a send restarts an idle agent. Probe read-only instead: `task_status` for a child, `t3_thread_read` with `afterPosition` for a launched thread. Collect each finished child per [the runtime's Delegation step 5](../../pstack-runtime/SKILL.md#delegation) instead of deep-reviewing inside the turn.
- **Each PR gets a verifier that is not its author,** from the `verifiers` role on a different model family than the worker when one is runnable. The owner merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### State

Keep the program's state under the runtime's [local state](../../pstack-runtime/SKILL.md#local-state) at `orchestrate/<project-slug>/`, by absolute path, never committed. `notes.md` tracks the program, its PRs, and their head-specific verdicts.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a control-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you cannot name the evidence, the unit is not scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text.
- Retry by mode: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. A long-lived owner takes the new model in place per [Top-level threads](../../pstack-runtime/SKILL.md#top-level-threads), and a child gets a fresh child on it. Two retries, then abandon the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user. When a table carries those facts better than prose, publish it per [Visual reports](../../pstack-runtime/SKILL.md#visual-reports). The decisions and PR links stay in the reply text.
